# Store metadata and privacy declarations

## Summary

Documents exactly what to fill in for Apple's App Privacy details and Google Play's Data Safety form, based on what NextWatch actually collects: an email for login, a ratings and taste history, and analytics tied to a user id but never to email or name. Getting this right matters beyond passing review: both stores will reject or later suspend an app whose declared data collection does not match its real behavior.

## Requirements

**User stories**:
- As the engineer, I want a clear, accurate answer for every question App Store Connect and Play Console ask about data collection, so the submission is not stalled on this step and does not misdeclare what the app does.

**Acceptance criteria**:
- **AC-1**: Every data type NextWatch actually collects (email, ratings and taste history, Sentry crash data, PostHog usage data) is listed with its purpose and whether it is linked to the user's identity.
- **AC-2**: The declarations state that data is deleted when an account is deleted, matching the real behavior built in the account deactivation and deletion child spec.
- **AC-3**: No data type the app does not actually collect (location, contacts, camera, health data, and so on) is declared, since NextWatch requests none of these.
- **AC-4**: An age rating and a support URL are decided, both required fields in each console that this spec had not yet addressed.

## Decision

**Chosen option**: declare four data categories (Contact Info, User ID, browsing or usage history, Analytics) identically in spirit across both consoles, each tied to the account deletion flow's real behavior. Full comparison and the research this rests on: see [rationale.md](../rationale.md).

## Feature design

**Data model sketch**: not applicable, this child is documentation and console configuration, not application data.

**State transitions**: not applicable.

**API surface**: not applicable, no code surface; both declarations are filled in directly in App Store Connect and Play Console, not generated by this app.

**Value sourcing**:
| Declared field | Value | Source |
|---|---|---|
| Apple App Privacy: Contact Info | email, used for account functionality, linked to identity | `backend/auth.py`'s `sign_up`/`sign_in`, the account's email |
| Apple App Privacy: User ID | the account id, used for app functionality | `get_current_user_id`, used across every authenticated endpoint |
| Apple App Privacy: browsing or usage history | ratings and taste history, used for app functionality (recommendations), linked to identity | the `ratings` table and `backend/recommend.py`'s taste vector |
| Apple App Privacy: Analytics | device and usage identifiers via Sentry and PostHog, linked to identity (a user id only, confirmed in `mobile/lib/telemetry.ts`'s `identifyUser`, never email or name) | spec 0003's telemetry setup |
| Google Play Data Safety: Contact Info / Activity or usage data / Device identifiers | same four items, mapped onto Play Console's own category names | same sources as above |
| Both consoles: data deletion practice | "the account is deactivated immediately on request, and permanently deleted, along with its ratings and notifications, 30 days later" — the exact declared wording, naming the grace period rather than a generic "on request" phrase | the account deactivation and deletion child spec's real, built behavior (`deactivated_at`, the 30 day purge job), not a claim independent of it |
| Age rating | 4+ / PEGI 3 (the lowest tier in each console), since the app has no user generated public content, no messaging between users, no mature content, and ratings/reviews are private to the account | filled in directly in each console's content questionnaire; no code produces this, the answer is fixed here so the questionnaire is answered consistently |
| Support URL | `${EXPO_PUBLIC_API_BASE_URL}/legal/support` | the legal screens and consent child spec's **AC-5**, `GET /legal/support` |

**Key invariants**:
- The declarations never claim less collection than the app actually does (a rejection and later suspension risk) and never claim more (an unnecessary privacy concession).
- If the account deletion flow's behavior changes later, these declarations must be updated to match; they describe real behavior, not a fixed document.

**Security model**: not applicable, no runtime access control; the risk here is a documentation and console configuration one (an inaccurate declaration), not an authorization one.

**Configuration required**: none.

**Critical test scenarios**: not applicable in the usual sense (no automated test verifies a console form); the check is a manual read through of both consoles' forms against this spec before submission, confirming every field matches AC-1 through AC-4.

## Build plan

1. Fill in Apple's App Privacy details in App Store Connect using the four categories in Value sourcing above, satisfies **AC-1**, **AC-2**, **AC-3**
2. Fill in Google Play's Data Safety form in Play Console using the same four categories mapped to Play's taxonomy, satisfies **AC-1**, **AC-2**, **AC-3**
3. Decide and set an age rating in both consoles' content questionnaires, satisfies **AC-4**
4. Decide and set a support URL in both consoles, reusing the legal screens child's hosted domain, satisfies **AC-4**

## Consequences

**Positive**: an accurate declaration in both consoles, matching real app behavior, reducing the risk of a review rejection or a later suspension for misdeclared data collection.

**Negative / tradeoffs**: this is manual console work that has to be redone by hand if the app's data collection ever changes (a new analytics vendor, a new data type); nothing here keeps the declaration automatically in sync with the code.

**Neutral**: no new library, endpoint, or schema change; purely a documentation and console configuration task.
