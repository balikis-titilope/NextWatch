# 0005. Backend Response Shape for Discover & Decide — Rationale

## Context

Journey 2, Discover & Decide (`docs/scope/scope.md` row 6), is ready to build: Home and Movie Detail are fully specified visually in `mobile/context/design.md` §6.4 and §6.6, against the backend's `/recommend` and `/movies/{title}/similar`. But reading the actual backend code (`backend/main.py`, `backend/recommend.py`, `backend/fetch_movies.py`) shows those two endpoints cannot support either screen as specified.

`/recommend` and `/movies/{title}/similar` both return the output of `recommend_for_user`, which selects only `["title", "release_date"]` plus a raw `predicted_score` (a cosine similarity, typically in a narrow band well under 1.0). Neither includes the movie's own `id`. Since the mobile route is `mobile/app/movie/[id].tsx`, a numeric id, there is today no way for a card tap to even navigate to Movie Detail.

Movie Detail needs far more: overview, cast with photos, runtime, genres, backdrop image, a trailer button, and a Where to Watch section with real provider logos. Some of these fields (`backdrop_path`, `runtime`, `tagline`, `trailer_keys`) exist in the bulk CSV `fetch_movies.py` produces, but are missing entirely from `recommend.py`'s own live single movie fetch path (`build_movie_row`, its own `fetch_movie_details`), which is what runs whenever a movie is resolved on the fly (via `/movies/resolve`, `/movies/{title}/similar` on an unseen title, or `/recommend`'s ad hoc `liked_titles` fallback). A movie resolved this way today would be missing almost everything Movie Detail needs. Cast photos and multi region Where to Watch data do not exist anywhere yet, not even in the bulk path: `fetch_movies.py` only ever captures cast member names (no `profile_path`), and flattens Where to Watch down to whichever single region (`NG` then `US`) was live at fetch time, discarding every other country TMDB actually returned.

Home also needs both a personalized "For You" row and a popularity based "Trending Now" row simultaneously, but `/recommend` returns exactly one ranked list per call, personalized or popular, never both; there is no way to get one of each from a single endpoint today.

Not deciding this blocks `/develop discover & decide` entirely: without a settled contract, the build would either invent fields ad hoc (risking a second, undocumented rewrite once gaps surface) or stall.

## Options considered

### Option 1: Extend the two existing endpoints, add two new single purpose endpoints, keep every call client composed

`/recommend` and `/movies/{title}/similar` gain the missing fields (`id`, `poster_path`) but keep their existing signatures. Two new endpoints are added: `GET /movies/trending` (wraps `recommend_popular`, computing each item's score against the caller) and `GET /movies/{id}` (the full Movie Detail payload, resolving live by TMDB id when not cached). Movie Detail's own Similar Movies row is a second, independent call to the now-extended `/movies/{title}/similar`, using the title the detail response just returned.

**Pros**:
- Every endpoint stays single purpose and independently cacheable by TanStack Query; nothing changes for callers of `/movies/{title}/similar` that only want similarity, not a full detail bundle.
- `GET /movies/{id}` being id keyed (not title keyed) matches the Expo route directly and needs no fuzzy title matching, which title based lookup exists for search, not for "load a known movie."

**Cons**:
- Movie Detail costs two round trips (detail, then similar) instead of one; on a slow connection, the Similar Movies row visibly loads after the rest of the screen.

### Option 2: One bundled "screen" endpoint per screen (e.g. a single call returning everything Home needs; Movie Detail bundles its Similar Movies row directly into the detail response)

**Pros**:
- Fewer round trips; a screen's data arrives in one response.

**Cons**:
- Couples unrelated concerns into one payload and one cache entry: Home's hero, For You, Trending, and Because You Liked rows have different refresh/staleness needs, but a bundled response invalidates and refetches all of them together.
- A bespoke, screen shaped endpoint is harder to reuse if another surface later needs just one piece of it (e.g. Search reusing the same card list logic).

### Option 3: Extend `POST /movies/resolve` into the general purpose detail lookup instead of adding a new route

**Pros**:
- Reuses an existing endpoint rather than adding a new one.

**Cons**:
- `/movies/resolve` is title keyed and exists specifically to fuzzy match and fetch-from-TMDB-if-missing, the wrong semantics for "load the detail screen for a movie whose id is already known." Overloading it with a second purpose (id based lookup for a known movie) makes its contract harder to reason about for both of its callers.

## Rationale

Option 1 was chosen because the app's data layer is TanStack Query, which is built around small, independently cacheable queries, not one large bundled fetch per screen (`mobile/AGENTS.md` §8, §3). Keeping the similar movies lookup as its own call also means Movie Detail's Similar Movies row can be refetched, retried, or shown loading independently of the rest of the screen, which a bundled response would prevent.

The original plan for that similar movies call was to reuse the existing `/movies/{title}/similar`, keyed by the title `GET /movies/{id}`'s own response would return. The cross check (below) found a sharper problem with that: Home's "Because you liked [X]" rows need the same lookup, but sourced from rating history, not from a freshly loaded detail response, and rating history is naturally keyed by `movie_id`, not by title. Going through a title at that point would mean taking an id the app already has, turning it into a title, then handing that title to an endpoint that fuzzy matches it back to an id, an unnecessary detour that reintroduces exactly the ambiguity risk (a same or similar titled movie resolving to the wrong id) an id keyed design was meant to avoid. `GET /movies/{id}/similar` closes this for both call sites at once: "Because you liked" rows use the `movie_id` already on the rating, and Movie Detail's own Similar Movies row reuses the id already in its own route, no title ever enters either path. `/movies/{title}/similar` is left exactly as it was, still available, just not used here.

Several value sourcing gaps surfaced while working through this and were resolved directly with the engineer, each is a real decision this spec is now the record of:

- **The movie id was missing everywhere.** None of `/recommend`, `/movies/{title}/similar`, or the underlying `recommend_for_user` return a movie's `id` at all, only `title` and `release_date`. Every card based row needs it to navigate; this spec adds it uniformly.
- **The score's scale did not match its own example, and a naive fix would have been dishonest or discouraging.** `predicted_score` is a raw cosine similarity (roughly 0 to 1, usually clustered well under that for this embedding model, and possible to land negative), but `design.md`'s own hero example shows "★ 4.2 match," a 0 to 5 looking number, and the existing `ScoreBadge` component just calls `.toFixed(1)` with no transform. Multiplying by 5, or even a plain `cosine * 100`, would not calibrate the number to anything meaningful: cosine similarity is a relative ranking signal, and for this model it clusters low even for genuinely strong matches, so a plain conversion would make the app's best picks look unimpressive (something like "35% match") every time. Several fixes were weighed and rejected before landing on the final one: a fixed rescale (stretching an assumed "typical" range to fill 0 to 100) was rejected because it requires guessing calibration constants with no real usage data to base them on; normalizing within each response (the top result in a given list scores near 100%) was rejected because it can make a genuinely good movie look bad purely for sharing a list with even better ones, and the same movie can show a different score in two different rows; percentile rank against the whole catalog was rejected because it answers "better than how many other movies," not what the engineer actually wanted, "how close is this to the movies I already love." The chosen calibration answers exactly that: a candidate's cosine similarity to the user's taste vector, divided by the average cosine similarity of that same user's own 4 or 5 star rated movies to that same taste vector (their personal "ceiling"), clamped to 0 to 100. It is personal (recalculates as a user's rating history grows), self-referential (no invented global constants, no comparison to other users), and stable (a movie's score does not depend on what else happens to be in the same list).
- **Trending Now's badge had no obvious source.** `recommend_popular` (what Trending Now is sourced from) ranks by global vote average and popularity, not personal taste, so it has no `predicted_score` of its own. The engineer chose to keep computing a personal match percentage for each popularity selected movie anyway, so the badge means the same thing everywhere in the app (how well this fits you), even though the row's selection criterion (popularity) is independent of that score.
- **`/recommend` could not produce two simultaneous rows.** It returns one ranked list per call; Home needs a personalized row and a popularity row at once. Rather than overload `/recommend` with a mode parameter, splitting a second concern into an endpoint whose contract was built around taste + mood blending, a dedicated `GET /movies/trending` was added, mirroring how `/movies/search` and `/movies/{title}/similar` already exist as separate, single purpose GETs.
- **Where to Watch was assumed to be a fixed region, and almost stayed one.** `fetch_movies.py` already hardcodes an NG then US fallback. The engineer's first instinct was to ask whether this was about physical location at all; once clarified that TMDB's Where to Watch is about which country's streaming catalog to check, not GPS, the engineer chose real per user data over the fixed fallback, a new `country` field on the account. Since Profile (where you would normally set such a preference) is not built yet, capturing it automatically from the device locale at signup, no new UI, was chosen over adding a field to the already built signup screen or a prompt during onboarding, and NG then US remains the fallback for the accounts (existing or locale detection failures) that end up with no stored country. TMDB's watch/providers API returns every country's listings in one call already; the engineer chose to cache all of them per movie (resolving to the user's country at request time) over a fixed short list, since a fixed list would partly defeat the point of a real per user country the moment a user's actual country fell outside it.
- **Trailers and missing data are not the same thing as a failed fetch.** A movie with no TMDB trailer hides the Watch Trailer button rather than showing it disabled (a button that does nothing on tap is a dead end). The engineer's original framing treated "a piece of the enrichment fails" as something that could happen independently per field; the cross check corrected this (see below), since TMDB's enrichment is one bundled call, not several independent ones. AC-10 now reflects the real two cases: the one call fails outright (network error, timeout, a non 200), which is a genuine error and caches nothing, versus the call succeeds but a sub field (like a trailer) is simply absent for that movie, which is normal and returns `null`, not an error.
- **Cast photos were a real, deliberate choice, not a default.** `design.md`'s "avatar placeholders" wording was genuinely ambiguous (generic silhouettes, or real photos styled as avatars); the engineer chose real TMDB photos, which is the reason `cast` gains a separate `{name, profile_path}` list alongside the existing pipe separated name only `cast` column (kept, since `filter_by_actor` and the Postgres upsert still depend on it), and why `recommend.py`'s live fetch path and `fetch_movies.py`'s bulk path both need updating to capture `profile_path` at all, since neither does today.

## Cross check findings

An independent model review of the drafted spec (a different, capable model, read only) found twelve gaps before this spec was finalized, ranging from correctness bugs to open decisions the draft had glossed over. All twelve were resolved and folded into the spec above; the two genuine decisions are covered in detail above (the score calibration, and the id based similar movies endpoint). The remaining ten were concrete fixes, not open questions, applied directly:

- **A migration re-run bug.** `fetch_movies.py` resumes from `data/fetch_progress_test.json`, skipping every id already marked done; the original migration plan's "just re-run it" would have silently done nothing. Fixed: the Migration plan now says to delete `data/movies_test.csv` and `data/fetch_progress_test.json` first, keeping `data/discovered_movies_test.json` (the discovery list needs no re-fetch).
- **New CSV fields had nowhere to go.** `save_to_csv`'s column list is fixed and the existing `cast`/watch provider columns are flattened strings, not structured data. Fixed: two new JSON columns (`cast_photos_json`, `watch_providers_json`), added alongside the existing columns, not replacing them.
- **A foreign key violation.** `GET /movies/{id}`'s live resolve path, as first drafted, never persisted a freshly resolved movie to Postgres, so rating it afterward would fail `ratings.movie_id`'s foreign key. Fixed: task 3 and task 10 now call `upsert_movie`, mirroring what `/movies/resolve` already does.
- **A missing `popularity` field.** `build_movie_row` (the live fetch path) never captured `popularity`, which `recommend_popular` sorts on; a live resolved movie would rank as `NaN`. Fixed: added to task 3's field list.
- **A crash on all neutral ratings.** `build_user_profile_from_ratings` raises when every rating is exactly 3 stars (no signal either direction), which the original cold start handling did not account for. Fixed: AC-3 and task 5/7 now treat "no usable taste signal" as including this case, returning `[]` or `null`, not a 500.
- **Trending's exact field wiring was unstated.** `recommend_popular`'s own return omits `id`/`poster_path`, and nothing named how its selected movies map back to `embeddings` for scoring. Fixed: task 8 now states both explicitly, and a `df` `RangeIndex` stability invariant was added since the scoring depends on it.
- **AC-10 was based on an inaccurate model of TMDB's API** (see above): restated around the real two cases, a failed call vs. an absent sub field.
- **`country` was silently dropped when email confirmation is required.** The original signup flow only threads new fields through `POST /auth/signup`'s immediate session path; `create_user_profile` is never called there when confirmation is required, only later in `/auth/verify-signup`. Fixed: `country` now flows through both, task 2 and AC-11.
- **Response field types were left implicit.** `genres` and `director` are pipe joined strings in `df`; the API surface table now states these as arrays in the response, and `trailer_key` as a single value (the first of TMDB's `trailer_keys`), not the plural list.
- **`GET /me/ratings`'s fields for "Because you liked" were unstated.** It already returns `movie_id`, `title`, and is already ordered most recent first, which turned out to be sufficient once the source moved to `movie_id` (per the id based similar endpoint decision above); no backend change was needed here beyond naming this explicitly in Value sourcing.
